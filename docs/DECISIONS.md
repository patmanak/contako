# Product decisions

These stable identifiers are referenced by code and tests. They record product
and interoperability choices, not an implementation log or release sequence.
The [target specification](SPECIFICATION.md) links the authoritative domain
contracts; [known limitations](KNOWN_LIMITATIONS.md) separates gaps from requirements.

| ID | Contract |
| --- | --- |
| D-001 | Specifications, source and public documentation are written in English. Operator communication preferences belong in ignored local instructions. |
| D-002 | The app owns a complete app-private local contact store; Proton is the remote peer; Android is an editable projection. |
| D-003 | Contact data is not application-level encrypted locally. |
| D-004 | Contako targets unattended synchronization after reboot and uses only the Keystore-protected derived user-key passphrase lifecycle selected by `D-060`; it never retains the Proton login/mailbox password. |
| D-005 | Concurrent contact edits require a whole-contact choice in Sync. Both versions remain durable until the choice is revalidated and applied; field-level merging is not offered. |
| D-006 | A concurrent remote edit and local deletion requires explicit review. Confirmed remote absence converges a pending deletion; a pending edit against a remote deletion retains local intent for recovery. No deletion time is invented. |
| D-007 | Android groups represent labels on the preferred email only; Android changes affect only that email and never invent an address. |
| D-008 | Android backups are disabled with manifest and explicit cloud/full/D2D exclusions. |
| D-009 | Nominal high load is 300 contacts/20 groups/about 10 contacts per group; robustness testing extends to 5,000 contacts/200 groups. |
| D-010 | Contako ships English, French, German, Spanish, Italian, Dutch, Polish, and Portuguese. |
| D-011 | TOTP 2FA is supported; security-key/FIDO login is not required initially. |
| D-012 | Contako supports one Proton account; internal ownership remains account-scoped for future evolution. |
| D-013 | Contako has no telemetry, analytics, advertising SDK, or remote crash reporting; only local redacted diagnostics may exist. |
| D-014 | Contako does not offer Android dynamic color/Material You; Contako's palette is used in light, dark, and follow-system modes. |
| D-015 | Public Proton repositories/libraries are preferred; custom endpoint code is narrow and isolated. |
| D-017 | Minimum supported version is Android 12 / API 31. |
| D-018 | Contako has public source and no ads or telemetry. Distribution follows the channel requirements in D-049/D-051 and Licensing. |
| D-019 | Contako original application code is licensed `GPL-3.0-or-later`; all compatible third-party notices are retained and every release receives a resolved dependency-license audit. |
| D-020 | Retain the Contako/octopus identity and a Proton logo with prominent unofficial-project disclosure; accept replacement if Proton objects. Clean up/redraw Contako illustrations as needed. |
| D-021 | Contako has no Contako-specific biometric/PIN app lock; device security remains the boundary because contacts are also exposed in Android's plaintext projection. |
| D-022 | Manual vCard import/export is outside the product target. |
| D-023 | Duplicate detection and merging are outside the product target; Contako MUST NOT merge another address book's contacts silently. |
| D-024 | Before updating or deleting an existing remote contact, fetch its verified complete card and compare it with the durable intent baseline. A changed baseline MUST retain both versions and block automatic upload. Sync lets the user choose Contako or Proton. Persist the choice against conflict generation, local revision and remote version; the serialized engine MUST revalidate it before applying it. New changes invalidate the choice. Keep snapshots until a confirmed write or atomic remote adoption; unknown/unrepresented properties remain preserved. The GET-to-write interval is not an atomic server precondition. |
| D-025 | Performance gates are 500 ms P95 cached content, 100 ms P95 local search, 300 ms P95 local save, 5 s no-change sync, 15 s ten-contact delta, 90 s 300-contact import, and 15 min 5,000-contact repair on the controlled reference profile. |
| D-027 | For a repeated canonical family exposed as a singleton by Android, project one primary occurrence; Android edit/delete affects only that occurrence and preserves hidden repetitions. Explain this in Contako. |
| D-028 | Android projects and edits only the canonical primary note; additional notes remain separate in Contako/Proton and are not concatenated. |
| D-029 | Contako keeps an ordered photo gallery; Android receives the preferred photo. The UI uses a circular primary avatar and may overlay the preferred vCard `LOGO` as a smaller bottom-right badge. |
| D-030 | Primary selection uses the lowest valid positive vCard `PREF`, then stable canonical order. Android may change the primary only through an unambiguous primary signal. |
| D-031 | Creating a new Proton contact requires at least one nonblank first name, last name, or display name; organization and email do not substitute for that name, and email remains optional. An existing Proton contact may legitimately become nameless through update and MUST remain representable, editable, and losslessly synchronized without a fabricated name. A new local/Android nameless draft remains action-required until named. |
| D-032 | Ordinary reconciliation uses a bounded paged lightweight contact directory through maintained Proton models. Hydrate new, changed or ambiguous contacts, and candidates for remote writes. A public paginated directory is not a server snapshot: absent IDs MUST receive a targeted structured absence confirmation before canonical deletion. Network, permission, generic HTTP errors and inconsistent pages MUST NOT authorize deletion. |
| D-033 | Queue immediate best-effort sync after durable edits/connectivity return, request Android periodic sync about hourly, check at app open when older than 15 minutes, retain manual sync, and provide no frequency picker. |
| D-034 | Ordinary sync uses any platform-permitted network. A manually requested full repair requires one confirmation when started off Wi-Fi; acceptance covers that pass even if network type changes. |
| D-035 | Full repair is user-initiated, cancellable at safe boundaries, may continue in background, keeps cached contacts usable, and uses a system notification only when Android requires it. |
| D-036 | Sync success and short offline periods are silent; user-action authentication conditions notify immediately, and a mutation blocked for 24 hours notifies once without repeated spam. |
| D-037 | Display canonical `FN` and sort with locale-aware collation; no first-name/last-name sort setting. |
| D-038 | Search locally across names, nicknames, emails, phones, organizations, and group names with case- and diacritic-insensitive matching; never use remote search. |
| D-039 | Contako requires a named deletion confirmation, then commits immediately without an undo timer; external editors retain their own interaction. |
| D-040 | Screenshots are allowed on contact screens; password, OTP, and recovery-code entry prevent capture and hide sensitive recent-app previews. |
| D-041 | Contako sign-out is confirmed; pending work defaults to Sync now or Cancel, with separately confirmed destructive discard. Android Settings account removal always performs scoped local cleanup and never deletes remote contacts. |
| D-042 | Contako offers an explicitly generated local sanitized diagnostic report with versions, capability states, aggregate counts/timings, sync outcomes, and error classes, but no payload, secret, stable ID, or raw server message. |
| D-043 | Use `minSdk 31` and `compileSdk`/`targetSdk 36`; test APIs 31, 34, and 36 plus the approved physical device; recheck Play policy before submission. |
| D-048 | The permanent Android application ID is `com.patmanak.contako`. |
| D-049 | Play uploads MUST use a dedicated owner-controlled, offline-backed upload key with Play App Signing and published certificate fingerprints. Separately signed F-Droid builds are a distinct update channel. Signing material MUST NOT enter Git; the prototype key MUST NOT become the public upload key. |
| D-050 | When Proton contact groups are unavailable for the account, ordinary contact sync remains operational; Groups stays discoverable with an explanation, unsupported mutations are disabled, and capability refresh enables them without reinstalling or deleting contacts. |
| D-051 | Publish public source and repository-hosted signed APKs, use Play internal testing before public distribution, then target Google Play and F-Droid for public distribution, subject to each channel's release checks. |
| D-052 | Detect contact-group availability from a maintained explicit Proton capability when available; treat generic Mail subscription state only as a hint and actual group/label API authorization as authoritative; refresh after account-plan changes. |
| D-053 | Contact-group capability is an account/session-scoped three-state value: `unknown`, `available`, or `unavailable`. Proton's maintained `hasPaidMail` user flag is a preflight hint only. A successful maintained group-list or group mutation proves `available`; only an explicit plan/entitlement/permission denial proves `unavailable`; authentication, network, rate-limit, 5xx, malformed, or unclassified failures remain `unknown`. The state refreshes at login/session restoration, user/subscription change, a stale app-foreground check, manual refresh, and immediately after an authoritative group response. Ordinary contact synchronization never depends on this state. |
| D-054 | Contako shows and edits only contacts owned by the connected Proton/Contako account; other Android accounts remain the responsibility of system contact applications. |
| D-055 | An incomplete Android-created contact is retained as a durable action-required local draft and withheld from Proton until valid. The Sync destination lists contacts requiring action; none are silently deleted. |
| D-056 | Group assignment is disabled for a contact without email; Contako never invents an address and removes an impossible external Android assignment during controlled reprojection. The reason is documented in the app's implementation notes/known limitations. |
| D-057 | Remote groups with duplicate names remain distinct by stable ID; deliberate duplicate creation warns first, and Contako never merges groups by display name. |
| D-058 | Use a canonical typed date-event list with at most one standard Birthday and one standard Anniversary plus repeatable labeled Other/Custom events. Full and yearless standard dates MUST sync with Proton. A custom event uses a validated compatible Proton encoding when available; otherwise it remains preserved locally and in Android, visibly marked not synchronized with Proton, and is never silently deleted. |
| D-059 | Contako generates no guessed Proton encoding for Android `Other`/custom date events. Only the singleton standard `BDAY` and `ANNIVERSARY` properties synchronize remotely, with full or yearless values preserved. Repeatable labeled custom dates remain canonical locally and in Android, display a clear “not synchronized with Proton” state, and survive edits/reprojection. Any unrecognized imported remote date property is preserved losslessly in the raw-property envelope but is not rewritten as a Contako custom date until a later approved mapping exists. |
| D-060 | Contako MUST NOT retain the Proton login/mailbox password for unattended contact cryptography. After an interactive successful unlock, it uses the pinned maintained Proton Core passphrase repository to persist only the derived user-key passphrase encrypted by Proton Core's Android Keystore primitive. This protected state may restore signing/decryption after process death and, after the device's first unlock, reboot. Missing, corrupt, invalidated, or unusable protected state stops headless sync and requires interactive reauthentication/unlock; it MUST NOT trigger a plaintext or custom password-cache fallback. Sign-out, Android account removal, session revocation, and failed password/key-transition recovery clear the retained passphrase and crypto context. |
| D-061 | Contako supports a Proton recovery code through the maintained Proton Core `SecondFactorProof.SecondFactorCode` flow when the server requests a code-capable second factor. TOTP and recovery code share one protected code-entry flow; the value is operation-scoped, never persisted/logged, cleared promptly, and submitted without local semantic guessing. Sanitized rejection remains retryable within server limits; unsupported/FIDO-only methods fail closed with an actionable message. |
| D-062 | If Android Contacts permission is denied or revoked, Contako remains usable for local/Proton browsing and editing while Android projection/ingestion is paused. A persistent top-of-app banner states that use is limited and system contact synchronization is unavailable; granting permission triggers controlled projection repair. |
| D-063 | Group deletion requires confirmation naming the group and member count; it removes the Proton/Contako group and its assignments but never deletes member contacts. Pending/incomparable remote changes follow the normal conflict policy. |
| D-064 | Every known Proton/vCard contact field family in the approved model is editable in Contako, including advanced `KEY`, `LANG`, `TZ`, `GENDER`, applicable `MEMBER`, `CATEGORIES`, `ROLE`, and `LOGO` values. Raw unknown properties remain preserved but are not exposed as an unsafe raw-vCard editor. |
| D-066 | Contako emits Proton WebClients' maintained standard item `TYPE` allowlists: email `home`/`work`/`other`, telephone `home`/`work`/`other`/`cell`/`main`/`fax`/`pager`, postal `home`/`work`/`other`, or no type. A new email or telephone custom label MUST be emitted as one lowercase `x-<token>` `TYPE`, normalized to ASCII letters, digits, and hyphens with a deterministic `x-custom` fallback. It MUST NOT generate `X-ABLABEL`. Imported unknown/custom type tokens and historical `X-ABLABEL` lines are preserved losslessly. Android custom labels for unsupported field families and unsupported standard types remain canonical and projected locally with a visible “not synchronized with Proton” marker; changing the value alone does not erase preserved remote metadata. |
| D-067 | Advanced fields use the pinned maintained Proton WebClients vCard model and RFC 6350 forms: `GENDER` is 0..1; `LANG`, `TZ`, `ROLE`, `LOGO`, `MEMBER`, `CATEGORIES`, and public `KEY` are 0..n. `LANG` is a language tag; `TZ` preserves text/URI/offset form; `GENDER` keeps the standardized component and optional identity text; `ROLE`/`CATEGORIES` are text; `LOGO` is a safe URI/data-image; and `KEY` is a validated public-key/certificate URI or text/data representation. `MEMBER` accepts the maintained Proton WebClients repeatable string form as a documented Proton compatibility extension and is never mapped to Proton labels; RFC group-card URI values remain preservable. New/edited serialized cards are capped at 10 MiB, scalar text at 16 KiB UTF-8, URIs at 8 KiB, decoded public-key material at 1 MiB, and decoded image/logo input at 10 MiB; imported values beyond an edit limit remain preserved but read-only/action-required. Any remote rejection retains the local edit pending/action-required and never strips unrelated or unknown properties. |
| D-068 | Current navigation is Contacts, Groups and Sync; account context, Settings, About, Usage and Sign out remain in the menu. About and Usage open separate pages directly. No redundant contacts-requiring-action entry or separate go-to-section control. |
| D-069 | Contact detail and editor follow the same progressive order: identity/media, email and groups, communication, organization/relationships, addresses, dates, notes, advanced known fields, then sync/destructive actions. Advanced fields MUST NOT be collapsed. Detail omits empty families; the editor keeps every family visibly discoverable with existing rows and an Add action, while adding repeatable rows progressively. |
| D-070 | Contako uses Material 3, the Android sans-serif/system font, Material Symbols Rounded for standard actions, an original semantic token set closely aligned with the current public Proton Mail Android design system, a purple scale centered on `#6D4AFF`, accessible light/dark/follow-system palettes, no dynamic color, and restrained reduced-motion-aware transitions. Proton source is design evidence, not a license to copy proprietary artwork or screen composition. |
| D-071 | Original editable artwork masters MUST preserve the approved Contako identity; the Proton mark stays standalone and removable. Source/provenance records MUST distinguish generated rasters from editable layered/vector masters. Current artwork is raster-only; see Licensing. |
| D-072 | Contako supports compact phone portrait and landscape plus expanded-window list/detail layouts for tablets and foldable-sized windows, without tablet-exclusive features. Window resizing preserves destination, selection, scroll/search state, drafts, and recovery flows. |
| D-077 | Retain the locale-aware alphabet fast-scroller in contact/group directories. |
| D-078 | Contako identifies to Proton with the observed generic-client convention `Other_<SemVer>+contako`, and sends the separate user agent `Contako/<SemVer> (Android)`. Interpreting `Other` as the generic third-party class is an inference from public client behavior and community discussion, not a documented Proton contract. Contako MUST NOT use an official Proton product identity, omit the `contako` build-metadata marker, or publish an artificial version. Because Proton Core's stock Android validator accepts only its official `product@version` grammar locally, Contako MUST bind a narrow fail-closed validator by equality to the single identity derived from the frozen build version and MUST regression-test every emitted release identity. Proton may display the session as an unknown application; Contako MUST disclose that limitation until Proton provides named third-party registration. |
| D-081 | The Android account name is the connected Proton account address. Removing the Contako Android account deletes all scoped Contako application data and Android projection data without deleting Proton contacts. Contako stores an account-scoped provider-epoch proof in the standard `ContactsContract.SyncState`; missing or mismatched proof after initialization is provider-state divergence and schedules bounded Android-only reconstruction from canonical Room state. Ordinary contact-row absence alone never proves a provider reset. |
| D-095 | Newly generated Proton contact cards MUST use the exact maintained WebClients vCard 4.0 composition: ranked `PREF` on generated `FN`, `EMAIL`, `TEL`, `ADR`, `KEY`, and `PHOTO`; signed `FN`, grouped `EMAIL`, then `UID`; private `N` and non-public fields; no invented `PRODID`; and no trailing CRLF. The decoder MUST continue accepting compatible vCard 4.0 input with different property order, optional `PRODID`, and trailing line endings. |
| D-096 | The maintained public directory supplies PUBLIC_DIRECTORY_FIELDS_ONLY coverage and LOCAL_INDEX_FINGERPRINT provenance; sizeBytes and modifiedAtEpochSeconds are absent. Production declares COMPLETE_PUBLIC_DIRECTORY, never authoritative server revision. Page totals, duplicates, counts and retained allocation are bounded during acquisition. Public fingerprints do not detect private-only edits; the contacts-only v6 event feed supplements them with an account-scoped durable cursor. The cursor advances with the completed inventory checkpoint, never on acquisition alone. Initial acquisition and server refresh require complete hydration. Targeted complete-card verification still protects pending writes under D-024; event positions are not contact revisions. |
| D-098 | Android photo projection MUST preserve canonical Proton bytes unchanged and generate separate bounded Android copies. It MUST seed a Binder-safe `Data/Photo` payload when required and attempt the journaled `display_photo` stream unless exact desired full-size and thumbnail readback already proves delivery. A pre-existing thumbnail alone MUST NOT prove stream completion. After bounded settling, an inline-only OEM result MAY converge only with exact expected generated bytes and valid ownership. Missing, empty, malformed, oversized, wrong-identity, dirty or unstable state MUST NOT be accepted. Photo binding/dirty acknowledgement MUST assert the observed provider version atomically and preserve unrelated native changes. |
| D-100 | After maintained Proton cryptography successfully decrypts and verifies a hydrated card, Contako MUST validate one bounded complete vCard 4.0 envelope and pass its original text directly to the bounded canonical/preservation parser. It MUST NOT require a generic parser/serializer round trip at that remote boundary. The canonical parser retains its size, structure, control-character, line/property/parameter, syntax, public-key, and identity checks. Locally generated upload cards MUST still pass the strict generic parse/serialization check before protection. |
| D-101 | The ordered runner MUST refresh and validate the durable Android interoperability context after Android ingestion and again after remote reconciliation plus outbox drain, immediately before each projection that follows those revision-changing boundaries. Final projection MUST use the second refreshed context. When that projection returns retry-waiting, it MAY be repeated locally only if another preflight proves that the projection itself advanced the durable context; these no-network replans MUST check cancellation and stop after four attempts. An unchanged context, exhausted cap, unavailable/cancelled/repair-required refresh, or local persistence failure keeps its normal closed outcome. |
| D-103 | A newly created contact group MUST use Proton contact-group palette color `#8080FF` by default. Contako's `#6D4AFF` application-theme primary remains a UI token and MUST NOT be reused as the wire default. Imported group colors MUST be preserved; deliberate recolor MUST use a Proton-supported palette value, and a rejected or unknown imported value MUST remain preserved and action-required instead of being silently coerced. |
| D-105 | Newly generated `PHOTO` and `LOGO` data-image values MUST be serialized as vCard URI values rather than text values. Contako MUST emit `VALUE=uri`, MUST NOT apply text escaping to URI delimiters, and, for an accepted inline data URI, MUST emit its validated raster MIME type as `MEDIATYPE`; preserved compatible parameters remain authoritative and MUST NOT be duplicated. |
| D-106 | Minified application builds MUST retain ez-vcard's runtime `ScribeIndex` registry and the existence of its standard `*Scribe` classes selected by runtime property names. Standard scribe classes MAY remain optimized and obfuscated; their unused members and non-scribe optional integrations remain shrinkable. The shared `VCardPropertyScribe` compiler-generated companions MUST survive. The bounded binary `PHOTO`/`LOGO` path MUST additionally retain its two concrete scribes, shared binary scribe/property base and compiler-generated companions, image properties/media types, data-URI parser, and bundled Base64 codec. A minified physical-device image-card parse MUST qualify this rule. |
| D-107 | The minified `benchmark` application variant MUST retain the public `ezvcard.Ezvcard` facade and every class appearing in its public method descriptors for calls originating in the separately minified instrumentation APK. This benchmark-only harness rule MUST NOT be copied to `release` without independent product evidence. |
| D-109/D-110/D-113 | At most ten concurrent remote reads and 25-contact durable commits; Android projection is capped at 16 independent slots, with shared/account work exclusive. Do not raise caps without measured physical evidence. |
| D-111 | Preserve remote PHOTO/LOGO references without automatic fetching. |
| D-112 | Structured seven-component ADR is authoritative; migrate a legacy scalar address into street without guessing a parser. |
| D-124 | Deployed Proton field compatibility MUST be established for custom-label/category/yearless forms. Preserve unsupported imported data and document known limitations rather than inventing successful remote support. |
| D-127/D-132 | Keep compact contact actions, aligned primary badges, usable Save/error feedback, full per-email group editing, original light/dark launcher support and concise menu/login copy. |
| D-129/D-130 | Check contact permission at startup; schedule sync after successful ready login; use bounded session-only password reuse for TOTP and build-gated typed diagnostics. |
| D-136 | Directories use a compact layout: compact bottom navigation, search collapsed by default behind a top-bar magnifier immediately before the account menu, automatic input focus on opening, and clear-and-collapse on the search cross. Preserve avatar/logo readability and the alphabet fast-scroller. Apply the same search interaction to Contacts and Groups; retain adequate space at large font sizes. |
| D-137 | Contact detail MUST show provided first and family names separately from the display-name heading. On Contako creation/edit Save, a blank or whitespace-only display name MUST be populated durably from trimmed first name followed by trimmed family name, omitting missing parts. Preserve an explicitly supplied display name; do not overwrite imported records merely during consultation. |
| D-138 | Returning from a contact MUST restore the previous directory position rather than jump to the beginning. Preserve row and pixel offset for unchanged results, including filtered lists and alphabet navigation; apply the shared behavior to Groups. Keep explicit active-tab reselection as the return-to-top action. |
| D-139 | Avoid the redundant identity gallery in contact consultation when only one image exists. Keep single-image preview accessible from the header badge; retain the gallery for multiple PHOTO/LOGO values and all editing controls. |
| D-140 | Contact date form fields MUST display day/month/year (`dd/MM/yyyy`) and open a calendar when tapped. Manual entry MUST use the same order; dates without a year MUST remain supported as `dd/MM`. Cancelling MUST preserve the original value. This presentation change MUST NOT alter synchronization formats or rewrite unedited imported dates. |
| D-141 | Reduce newly selected contact images using the documented Proton-derived sizing policy. The sizing policy and intentional Android adaptations are documented in Contacts. This selection-time optimization MUST preserve orientation and transparent logos, avoid enlargement/cropping, and MUST NOT resize existing/imported image bytes during ordinary edits or sync. |
| D-142 | Android photo projection MUST retain a durable receipt of the provider-produced representation after a synchronous ownership/version-guarded write. Canonical originals remain separate. Unchanged receipt bytes MUST retain the original during unrelated native edits; differing bytes require native photo capture. No perceptual tolerance or arbitrary adoption after an interrupted write is permitted. See Contacts for bounded input, readback and recovery guards. |
